# Isometric pixel-art city map — project plan

Goal: a zoomable, pannable isometric pixel-art map of a real city, in the spirit of
isometric.nyc and tinyrj.com. Every tile is generated by an image model from an isometric
render of the city's 3D data, and the result is served as a static tile pyramid.
Whether it becomes a game is open.

Pilot area: **Södermalm, Stockholm** (`config/area.yaml`). Prove the whole pipeline end to end
on the pilot, then scale.

## Status (2026-11-04)

- **Data source: Google Photorealistic 3D Tiles, in closed mode** (user decision, 2026-11-04).
  See "Closed mode" below.
- **Done:** tile planner, headless renderer on Google 3D Tiles, seam checks, pilot rendered
  north-up (32 tiles), training-tile selection, tile pyramid + viewer (prototype map of the
  renders), Gemini image-model script (`pipeline/stylize.py`).
- **Next:** Phase 3 — style examples: write prompts for *photo* renders, iterate on ~10 tiles.
- **Waiting on (user):** style choice and own reference images; replies to the licence requests
  (Stockholm stad, Hexagon, HERE — drafts written 2026-11-04).

## Closed mode

Google's Map Tiles terms (EEA, read 2026-11-04) forbid storing renders, creating content based on
them, training AI on them and selling them. Live in-browser display with attribution is allowed.
The user chose to continue privately with Google anyway, since a public or paid product isn't
decided yet. Rules while in closed mode:

- Nothing derived from Google is published, shared or sold. Renders, generated tiles and
  pyramids stay local (`data/`, `dist/` are git-ignored); the viewer only runs on localhost.
- Generated tiles must credit "Map data ©Google" in the viewer.
- Before anything goes public: switch to a licensed source (see "Licensed source" below) and
  re-render; keep the pipeline source-independent so that is a re-render, not a rewrite.
- Fine-tuning a model on Google-derived pairs is explicitly prohibited by the terms; treat any
  such model as throw-away, private experiment only.

Key clauses (EEA ToS §3.3.2(a) no "pre-fetch, index, store, reshare, or rehost … outside of the
Services"; (b) no caching; (c) no "content based on Google Maps Content … (v) … train, test,
validate or fine-tune" AI; §3.3.1(b) no "sell, resell, sublicense, transfer, or distribute").

## Phase 0 — Decisions and setup

- [x] Pilot area and boundary: `config/sodermalm.geojson` (~1.9 km², Slussen–Mariaberget–Katarina).
- [x] Camera: 2:1 isometric, 30° elevation, **looking north** (`look_azimuth_deg: 0`): north points
      straight up on the finished map (user requirement). Training pairs may use another bearing.
- [x] Scale: **0.25 m/px**; 1024 px render tiles split into 2×2 quadrants of 512 px (a half-tile
      slide = 1 quadrant, 4-bit infill masks, as Isopolis and isometric.nyc).
- [ ] **Style**: pick a direction and collect 5–10 own reference images in `style/references/`
      (git-ignored). Current references are screenshots of tinyrj/tinygyn: private use only.
- [x] Google Maps Platform key (`GOOGLE_MAPS_API_KEY` in `.env`); Vertex AI via ADC
      (project `crafty-haiku-422`, global endpoint, no key needed).
- [x] **Local image model on the user's PC** (RTX 3070 8 GB, 32 GB RAM, Windows 11, LAN
      192.168.86.32, user `nilss`, SSH key login from the Mac). Set up 2026-11-04, see `gpu/`:
      ComfyUI 0.44 + PyTorch 2.10/CUDA 12.8 + Nunchaku 1.2.1 in `C:\ai\ComfyUI`; model
      `svdq-int4_r32-qwen-image-edit-2509-lightning-4steps-251115` (int4: RTX 30 can't run fp4) +
      `qwen_2.5_vl_7b_fp8_scaled` + `qwen_image_vae` (all Apache 2.0). Runs as scheduled task
      `ComfyUI` at boot, port 8188 for the local subnet only. Client: `pipeline/comfyui.py`,
      `stylize.py --backend comfyui`. ~45 s first image (model load), then ~22 s per 1024² tile.
      → first test (`style/prompts/photo-v1.md`, tiles 0_-1, 0_0): geometry, buildings and
        colours kept very faithfully (Södra tornet, Bofills båge right), but hardly any pixel-art
        styling: a smoothed/painted photo. Erased the Slussen construction area in 0_-1.
        Expect to need a style LoRA (Phase 4) or more steps / prompt work; fine-tuning a 20B model
        won't fit in 8 GB: train in the cloud, generate locally.
      → the PC must not sleep while serving (power settings changed by the user).

## Phase 1 — 3D city data

- [x] Google Photorealistic 3D Tiles streamed into three.js with `3d-tiles-renderer`
      (`render/src/scene.ts`): ECEF → plan ENU transform on `tiles.group` in float64; errorTarget
      2 px; tile cache 3 GB (one view needs ~1 GB; a full cache silently refuses finer tiles);
      a tile is "settled" when nothing is queued/loading/refused and the visible set is stable;
      failed downloads (e.g. 503) fail the tile, the page reloads and retries once.
- Known data issues: Slussen partly shown as a construction site (Google's capture date unknown;
  no date control in the API); floating mesh blobs in a few places (e.g. near Rålambshov);
  light patch edges in water; a few semi-transparent pixels where the mesh has cracks.

**Licensed source (for anything public) — open, waiting for replies**
- [ ] **Stockholm stad**: textured LOD2 city model ("105 000 texturised buildings … texturised
      with true orthophoto and oblique imagery"); licence unpublished, priced by taxa.
      Ask geodataservice@stockholm.se (draft written).
- [ ] **Hexagon HxGN Content Program, Metro HD**: Stockholm captured 2021 (obliques, mesh, LOD2);
      "flexible data use terms allow users to create derived products" — ask sales (draft written).
- [ ] **HERE Premier 3D Cities**: Stockholm listed, games named as a use case; textures unconfirmed.
- Ruled out (terms or content): Mapbox, Microsoft (Azure/Bing/Flight Simulator), Apple, Esri,
  Cesium ion, MapTiler, Vexcel, Mapillary (share-alike), Lantmäteriet raw photos (nadir only).
- Tried and set aside: **OSM+Lantmäteriet option** (extruded OSM boxes, facades invented by the
  image model): user rejected it — "the city is hardly recognizable … it differs a lot from the
  original". Code, prompts and the full source research (Lantmäteriet products and licences,
  Stockholm stad data, OSM coverage, facade-imagery vendors) are on branch
  `osm-lantmateriet-option`.

## Phase 2 — Isometric renderer

- [x] Orthographic camera; basis, frustum and tile targets read from the plan JSON.
- [x] Grid planner `pipeline/plan_tiles.py`: the only place tile geometry is computed. Tile ids
      `x_y` = screen column/row; north-up: `x`+1 = 256 m east, `y`+1 = 512 m south (ground).
      Infill windows at any quadrant offset are cut from base renders via `window_rect_px()`.
- [x] Headless batch export: `npm run render -- render --plan … --out data/renders/<area>
      --block=… | --tiles=… | --tiles-file … | --all`; skips renders made for the same tile
      geometry; JSON sidecar per tile (attributions, stats). `--source test` = synthetic box city
      (no API) for geometry checks. Interactive check: `npm run render -- view --plan …`.
- [x] Seams: neighbouring renders agree in shared pixels (Google: mean ≤ 0.023, float rounding at
      triangle edges), so `overlap_px` = 0 is enough for renders. Checked with
      `pipeline/stitch_block.py` (overlap diff + step ratio; the step ratio depends on content).
- [x] Pilot rendered north-up: 32 tiles in `data/renders/sodermalm/`, no visible seams.
- [ ] Optional extra passes (depth, masks) as model input, if Phase 3/4 needs them.

## Phase 3 — Style examples (training pairs)

- [ ] Prompt for **photo renders** → pixel art in the chosen style (strict palette, hard pixel
      edges, geometry kept exactly). Save versions in `style/prompts/`. Earlier prompts were for
      OSM box renders (branch `osm-lantmateriet-option`); lessons that carry over: send style
      references as extra images, keep each building's colours from the input, forbid invented
      water (the script adds a "no water" line for dry tiles), give landmark hints per landmark
      (not per tile) and check them against photos.
- [ ] Iterate on ~10 varied tiles with `pipeline/stylize.py` (Vertex AI; Nano Banana Pro was
      clearly better than Nano Banana 2 on landmarks; $0.13 vs $0.067 per 1K image; `--ref`,
      `--hints-dir`, `--pixel N` = half-resolution + shared palette; 429s retried).
      Pixel post-process: build the shared palette from several tiles including water.
- [ ] Generate 100–300 pairs from the training area and review by hand.
      → `config/training.yaml` (~40 km² of central Stockholm, same grid as the pilot, checked by
        `tests/test_training_area.py`); `pipeline/training_tiles.py` picks a checkerboard (no
        overlapping windows), drops near-pure water, thins evenly.
      → 150 tiles were selected and rendered at the old 225° bearing (`data/renders/training/`;
        the list in `data/plan/training-tiles.txt` refers to the 225° plan). Either re-plan at 225°
        to reuse them, or pick and render a new north-up set (one session).
- [ ] Artefact screening before spending generation calls (floating blobs, holes).

Deliverable: `data/training_pairs/` with a curated set + `manifest.csv`.

## Phase 4 — Fine-tune our own model

Why: consistent style across thousands of tiles, cheaper than a cloud model per tile, and can
run on the user's NVIDIA GPU. (Closed mode: private experiment only.)

- [ ] Base image-editing model that supports LoRA (Qwen-Image-Edit, FLUX Kontext, …).
- [ ] Two tasks in one model: *generate* (render → pixel art) and *infill* (render + finished
      neighbour quadrants → continuation). Isopolis: 4-bit TL/TR/BL/BR masks, all 15 patterns;
      Qwen-Image-Edit-2511 + LoRA r=16, 2,000 steps, 1× H100; 100 pairs beat 60.
- [ ] Evaluate on held-out tiles: style match, geometry, seams. Iterate on data first.

Deliverable: a model + `pipeline/generate.py`.

## Phase 5 — Generate the whole map

- [ ] `data/map.db` (SQLite): one row per quadrant — position, render path, output, status
      (`pending / generated / approved / rejected`), notes.
- [ ] Sliding 1024² window stepped by one quadrant; seeds first, then a seam planner grows outward
      in waves (Isopolis: 440 renders → 1,519 generations in 67 waves). Don't generate between
      finished quadrants on opposite sides; fill strips as 2×1 blocks with gaps, then the gaps.
- [ ] Rejection guard vs a context-free baseline; water windows stamped instead of generated;
      regenerate a bad quadrant with verified context around it.
- [ ] Pixel-overlap experiment for *generated* tiles (renders are exact at `overlap_px` 0); crop,
      never blend.
- [ ] Resumable overnight batch runner.
- [ ] **Review app** (`review/`): generated quadrants over a map, reject/regenerate, render vs
      result side by side.

Deliverable: every quadrant in the pilot approved.

## Phase 6 — Tile pyramid

- [x] `pipeline/build_pyramid.py`: pyvips stitch over the plan grid + Deep Zoom (512 px, WebP);
      `--style photo` (box shrink) or `pixel` (lossless, nearest); `manifest.json` with origin,
      north direction, screen→lon/lat, attributions. Needs a quadrant mode for generated art.
- [x] Prototype: `dist/sodermalm-renders/` (north-up renders, 8192×4096, 11 MB).
- [ ] Lower zoom levels for pixel art: compare downscaling methods (box + palette snap, …).
- [ ] Optional: single PMTiles file.

## Phase 7 — Web viewer

- [x] `viewer/` (Vite + OpenSeadragon): `npm run viewer -- dev --map ../dist/<map>` or `build`
      (static site in the map folder). Mini-map, compass, lat/lon under the cursor, attribution,
      shareable `#x,y,zoom` (plan screen px, stable across rebuilds).
- [ ] `image-rendering: pixelated` at high zoom, smooth at low zoom (only `style: pixel` so far).
- [ ] Later: place labels, day/night palette, animated details (boats, trains on real timetables).

## Phase 8 — Hosting (only after leaving closed mode)

- [ ] Static hosting + CDN (Cloudflare R2/Pages, S3 + CloudFront, Netlify), long cache headers,
      versioned folders.

## Rough budget (pilot)

- Google 3D Tiles: one session per render run (~10–30 s per tile).
- Style examples: Nano Banana Pro $0.13 / Nano Banana 2 $0.067 per 1K image (Vertex global);
  batch mode half price. A few hundred images → ~$20–60.
- Fine-tuning: a few GPU-hours (or local GPU).

## Known risks

| Risk | Mitigation |
|---|---|
| Google terms forbid publishing, deriving, training and selling | Closed mode; licensed source (Stockholm stad / Hexagon / HERE) before going public |
| Outdated source data (Slussen) | Patch affected quadrants with own reference photos (buildings may be freely depicted, URL 24 §) |
| Existing map: **tinysthlm.com** (Google 3D Tiles → Qwen + tiny.london LoRA, free, non-commercial) | Own style; licensed source if it ever goes public |
| Image-model licences (some are non-commercial) | Check before any public use |
| Seams between tiles | Half-tile sliding-window infill + seam planner + review app |
| Water, trees, glass look wrong | Over-represent them in training pairs; stamp water |
| Style drifts across the map | Fine-tuned model + shared palette |
| Muddy zoomed-out levels | Careful downscaling (Phase 6) |
