# Isometric pixel-art city map — project plan

Goal: a zoomable, pannable isometric pixel-art map of a real city, in the spirit of
isometric.nyc and tinyrj.com. Every tile is generated by an image model from an
isometric 3D render of the real city, and the result is served as a static tile pyramid.

Pilot area: **Södermalm, Stockholm** (placeholder — change in `config/area.yaml`).
Start small (≈1–2 km²), prove the whole pipeline end to end, then scale.

## Status (2026-11-03)

- **Done:** pilot boundary, camera angle, Python setup (`uv`, `pyproject.toml`), tile
  planner `pipeline/plan_tiles.py` + geometry tests (`tests/`), incl. canonical quadrant grid
  (2×2 × 512 px), `window_rect_px()` for half-tile sliding windows, optional `overlap_px`.
  Renderer `render/` (three.js + 3d-tiles-renderer, headless via Playwright on the Metal GPU,
  plus interactive `view` mode) and `pipeline/stitch_block.py` (stitch + seam metrics). 3×3
  seam test passed on a synthetic test scene: neighbouring renders are pixel-identical in
  shared pixels.
  Google 3D Tiles render works (key in `.env`): 8 tiles of the −1..1 block in
  `data/renders/sodermalm/`, ~5–13 s each; tile naming/orientation verified by the user.
  Google renders are now repeatable and neighbours agree in shared pixels (3×3 check passed).
  Scale fixed at **0.25 m/px**; whole pilot rendered (34 tiles, `data/renders/sodermalm/`,
  stitched `data/stitch/sodermalm-all.png`, 10240×6144, no visible seams).
  Training set: 150 varied render tiles from a ~40 km² central-Stockholm training area
  (`data/plan/training-tiles.txt`).
  Prototype map (Phases 6–7 first, with renders instead of pixel art): `pipeline/build_pyramid.py`
  → `dist/sodermalm-renders/` (Deep Zoom, 12 MB) + OpenSeadragon viewer in `viewer/`.
- **⚠ Google terms (read 2026-11-04, EEA terms apply):** storing renders, publishing them,
  making pixel art from them, selling a game with it and training a model on them are all
  prohibited (details under Phase 0). The pipeline built so far is fine; the *data source* has to
  change for anything public or paid. Keep the prototype private; no more Google rendering
  until decided.
- **Next:** user decides the data source (Phase 1b open data; see Phase 0 note), then style.
- **Blocked on (user):** data-source decision, style + reference images, camera direction
  confirmation.

## Phase 0 — Decisions and setup (½ day)

- [x] Pick the pilot area and draw its boundary polygon (GeoJSON in `config/`).
      → `config/sodermalm.geojson`: rough ~1.9 km² box (Slussen–Mariaberget–Katarina); refine on geojson.io.
- [ ] Decide the **style**: SimCity 2000 / Ghibli / Habbo / something own. Collect 5–10
      reference images in `style/references/` (for our eyes and prompts — not to copy).
- [x] Fix the **camera**: classic 2:1 isometric (≈30° elevation, 45° azimuth), one fixed
      direction for the whole map. Decide which way is "up" (tinyrj shows an N indicator).
      → looking SW (`look_azimuth_deg: 225`), elevation 30°; north points screen-down-right.
- [x] Fix the **scale**: metres per output pixel (e.g. ~0.5 m/px) and tile size
      (1024×1024 render → 1024×1024 pixel art, split into 2×2 quadrants of 512 px).
      → 2×2 of 512 px, matching Isopolis and isometric.nyc: a half-tile slide = 1 quadrant, and
        infill masks are 4-bit (15 context patterns) instead of 16-bit with 4×4.
      → **0.25 m/px** (user, 2026-11-04). Pilot = 34 render tiles, 106 quadrants. Google detail
        holds up at this scale (one tile = 256 m wide, ~200 visible Google tiles, ~400 MB cache).
        Old 0.5 m/px renders kept in `data/renders/sodermalm-0.50mpp/` for comparison only.
- [ ] Accounts / keys: Google Maps Platform (Map Tiles API), Gemini API (Nano Banana Pro),
      a fine-tuning provider (Oxen.ai, fal.ai, Replicate or own GPU). Put keys in `.env`.
      → `GOOGLE_MAPS_API_KEY` set (2026-11-03).
      → user wants to run image generation **locally on their NVIDIA PC** (later). Nano Banana is
        cloud-only (no weights), so local means an open model: Qwen-Image-Edit (Isopolis' choice,
        LoRA-tunable) or FLUX.1 Kontext [dev]. Open: GPU model / VRAM, and whether Phase 3 style
        examples still come from Nano Banana (cloud) with only Phase 4–5 running locally.
- [x] **Check terms of use.** Google Photorealistic 3D Tiles have restrictions on caching,
      offline use and derivative works. Read them before scraping at scale, and keep the
      open-data alternative (Phase 1b) in mind.
      → read 2026-11-04 (not legal advice). Swedish billing → **EEA ToS** (cloud.google.com/terms/
        maps-platform/eea, mod. 2026-08-26) + EEA Service Specific Terms (mod. 2026-10-28) + Map
        Tiles policies (2026-11-02). Key clauses: §3.3.2(a) no export/scrape, "pre-fetch, index,
        store, reshare, or rehost … outside of the Services"; (b) no caching (no Map Tiles exception);
        (c) "will not create content based on Google Maps Content … (v) use … to train, test,
        validate or fine-tune [ML/AI] models"; §3.3.1(b) no sell/distribute; policies: no "Offline
        uses", promo video ≤ 30 s only. Geo Guidelines: don't "significantly alter how Google Maps …
        would look". Verdicts: live in-browser display with attribution = OK; storing PNG renders
        = prohibited; public map of renders = prohibited; pixel art from renders (free or paid
        game) = prohibited; training on renders = explicitly prohibited. Isopolis used the same
        pipeline and says "This sort of scraping is actually against Google's TOS."
      → consequence: Google 3D Tiles can only be a private feasibility test. For a public map or
        a paid game the source must be open data, see Phase 1b. Existing Google renders in
        `data/renders/` and `dist/sodermalm-renders/` are stored content: user to decide whether
        to delete them.
- [ ] **Decide the data source** for the real map (user). Candidates, all to be verified per
      product: OpenStreetMap (ODbL; rendered images are "produced works", any licence incl.
      commercial, credit "© OpenStreetMap contributors"); Lantmäteriet open data (CC0 / CC BY 4.0,
      some products need special terms); Stockholm stad's textured 3D mesh (licence unknown,
      ask the city); Helsinki-style CC BY city meshes as a reference.

## Phase 1 — Get 3D city data (1–3 days)

**1a. Google Photorealistic 3D Tiles (recommended first try)**
- [ ] Stream tiles for the pilot bounding box with `3d-tiles-renderer` (NASA-AMMOS) in three.js.

      → interactive check: `npm run render -- view --plan ../data/plan/sodermalm.json` (arrows/±).
- [ ] Cache fetched tiles locally (within what the terms allow) so re-renders are cheap.

**1b. Open-data fallback (Sweden)**
- [ ] Investigate Lantmäteriet open elevation/laser data and building footprints, and
      City of Stockholm's 3D city model / open data. Combine footprints + heights into
      simple meshes. Less texture, so the image model has to invent more.

Deliverable: `render/` can show the pilot area in 3D in a browser.

## Phase 2 — Isometric renderer (2–4 days)

- [x] three.js scene with an **orthographic** camera at the fixed isometric angle.
      → camera basis, frustum and tile targets are read from the plan JSON, never recomputed.
- [x] Function `renderTile(cx, cy) → PNG`: centres the camera on a world coordinate and
      renders a 1024×1024 image. Run headless with Playwright to batch-export.
      → `npm run render -- render --plan … --out data/renders/<area> --block=… | --tiles=… | --all`.
        Waits until the tileset is fully loaded for N idle frames (`--settle-frames`), skips
        existing PNGs (resumable), transparent background = no data. `--source test` renders a
        synthetic box city for geometry checks without API calls. Headless Chromium gets the real
        GPU (`--use-angle=metal`, "ANGLE Metal Renderer: Apple M1").
- [x] Grid planner (`pipeline/plan_tiles.py`): converts the boundary polygon into a grid of
      tile centres in *isometric screen space*, so neighbouring tiles line up exactly.
      → quadrants are the canonical unit (`quadrants` in the plan JSON). Render tiles abut on
        the quadrant grid and are rendered `overlap_px` larger per side (default 0). Because the
        camera is orthographic and fixed, infill windows at any quadrant offset are cut from the
        base renders via `window_rect_px()`; no extra renders needed.
- [ ] Optional extra passes per tile: depth map, flat "whitebox" render, water/vegetation
      mask — useful as extra model input later.
- [ ] Verify: render 3×3 neighbouring tiles, stitch them, and check there are no gaps,
      overlaps or seams. Renders of shared pixels must match exactly (the infill-window
      approach above depends on it); also check whether edge pixels differ (AA, LOD) and
      whether `overlap_px` > 0 is needed to crop them away.
      → test scene, 8 tiles of the −1..1 block (1_1 isn't in the plan): with `overlap_px` 8 the
        shared pixels of every neighbouring pair are identical (max diff 0), with MSAA on. So for
        renders, overlap isn't needed. Changing `overlap_px` changes the frustum and shifts ~80 of
        9.4 M pixels by float rounding at triangle edges, so re-render everything if it changes.
      → the "step ratio" seam metric depends on content (0.2–1.9 on the box city at seams that are
        exact); use it to compare generated vs render at the same seam, not as an absolute score.
- [x] Repeat the 3×3 seam check on Google 3D Tiles (LOD selection per tile could differ at edges).
      → first run (errorTarget 2, settle 10 frames): shared pixels differ (mean 0.002–8.8, max up to
        175), and so does the same tile rendered twice, so it's render nondeterminism, not geometry.
      → cause: the default tile cache (0.4 GB) is too small. One view at errorTarget 2 needs
        ~1 GB, a full cache silently refuses finer tiles, and `loadProgress` still reads 1. Fix:
        `--cache-mb` (default 3000), settle requires nothing queued/loading/refused *and* an unchanged
        visible-tile set for N frames, and fail loudly if the cache is full. Visible-tile count and
        cache size go into each sidecar JSON.
      → after the fix: the same tile rendered fresh vs warm differs in 2 px; neighbours' shared
        pixels (overlap 8) mean 0.001–0.023, max ≤ 33 (float rounding at triangle edges). ✔
        ~10–30 s per tile, ~650 visible Google tiles per view.
      → tile layout checked by the user against the stitched block: `x` = screen column
        (+1 = 512 m NW), `y` = screen row (+1 = 1024 m NE), north points screen-down-right.
      → ~70 px per tile are semi-transparent (mesh cracks show the clear colour). Decide later:
        fill them (e.g. dilate neighbours) or render on an opaque fixed colour.

Deliverable: `data/renders/{x}_{y}.png` for the whole pilot area.

## Phase 3 — Style examples with Nano Banana Pro (2–3 days)

- [ ] Write a prompt that converts one render into pixel art in the chosen style
      (strict palette, no anti-aliasing, keep geometry exactly in place).
- [ ] Iterate on ~10 varied tiles (dense blocks, water, parks, bridges, hills) until the
      style is stable. Save prompt versions in `style/prompts/`.
- [ ] Generate 100–300 **(render → pixel art)** pairs. Review by hand, reject bad ones.
      → the pilot alone gives only 34 tiles / 79 distinct 2×2 windows, heavily overlapping and
        dominated by Söder blocks + water. Use a separate **training area**: same origin, camera and
        scale (so same grid), larger boundary sampling varied Stockholm (Gamla stan, Djurgården
        parks, Hammarby Sjöstad, Kungsholmen, bridges, quays, Skeppsholmen). Pick ~150 tiles
        spread for variety. Renders are cheap (~10 s, a session per run); Nano Banana calls are
        the cost.
- [x] `config/training.yaml` + boundary, sharing origin/camera/scale with `area.yaml`; plan it with
      `plan_tiles.py` and choose varied tiles.
      → `config/training.geojson`: ~40 km² box of central Stockholm (17.995–18.130 E,
        59.300–59.345 N) → 355 tiles. `tests/test_training_area.py` checks the grid is shared.
      → `pipeline/training_tiles.py`: `candidates` = checkerboard (no two tiles share an edge, so
        training windows never overlap) → 178; `pick` drops near-pure water (> 75 % water blocks,
        detector = dark + blue-ish + smooth 16 px blocks, tuned on pilot) and missing data, then
        thins evenly to 150 → `data/plan/training-tiles.txt` (+ `.scores.json`).
      → done 2026-11-04: 178 candidates rendered (`data/renders/training/`, one session, ~3–13 s
        per tile), 13 dropped as open water, 2 excluded (9_-1, 8_0: a floating smeared mesh blob in
        Google's data near Rålambshov, reproducible on re-render) → **150 tiles**: 89 no water,
        45 some water, 16 lots. Good spread: Gamla stan, stone-city blocks, modern housing, rail
        yards, parks, forest, quays, bridges.
- [ ] Artefact screening: only eyeballed on a thumbnail sheet. Add a cheap automatic check (large
      low-detail/blurry regions) or do it in the review app before spending generation calls.
- [ ] Post-process: snap to the palette, enforce hard pixel edges (nearest-neighbour
      downscale → upscale).

Deliverable: `data/training_pairs/` with a curated set + `manifest.csv`.

## Phase 4 — Fine-tune our own model (2–4 days)

Why: consistent style across thousands of tiles, and far cheaper/faster than calling
Nano Banana per tile.

- [ ] Choose a base image-editing model that supports LoRA fine-tuning
      (e.g. Qwen-Image-Edit or FLUX Kontext — check what the provider supports).
- [ ] **Two tasks in one model:**
  1. *Generate*: render → pixel art.
  2. *Infill*: render + already-finished neighbour quadrants (pasted in) → pixel art that
     continues them seamlessly. Build these inputs by masking parts of the Phase 3 pairs.
     Isopolis: 4-bit TL/TR/BL/BR masks (1 = keep as context, 0 = generate), all 15 patterns.
- [ ] Reference point: Isopolis used Qwen-Image-Edit-2511 + LoRA r=16, 2,000 steps, 1× H100;
      a 100-pair set beat a 60-pair set. Training pairs made with Nano Banana.
- [ ] Train, then evaluate on held-out tiles: style match, geometry faithfulness, seams.
- [ ] Iterate on data, not just hyperparameters (add more water/tree examples — known weak spots).

Deliverable: a model endpoint + `pipeline/generate.py` that calls it.

## Phase 5 — Generate the whole map (ongoing)

- [ ] SQLite database (`data/map.db`) with one row per **quadrant**: position, render path,
      generated PNG, status (`pending / generated / approved / rejected`), notes.
- [ ] Generation order: **sliding 1024² window, stepped by half a tile (1 quadrant)**, so
      every window after the seeds has ≥1 finished quadrant as context (Isopolis §2d: "slide
      by half image in any direction"; isometric.nyc does the same with quadrant infill).
      Seed a few windows, then a seam planner greedily grows outward in waves (Isopolis: 440
      renders → 1,519 generations in 67 waves, ~3.5× calls). Rules (isometric.nyc tasks/012,
      019): don't generate a window between finished quadrants on opposite sides; fill strips
      as 2×1 blocks with 1-quadrant gaps, then the gaps. Each window writes only its
      mask-0 quadrants.
- [ ] Rejection guard: compare each generation to a baseline (context-free) inference of the
      same window; regenerate if it drifts too far in style/palette.
- [ ] Water: skip windows above a water threshold and stamp a water texture instead.
- [ ] Regenerate a bad quadrant by placing a 2×2 window with verified context on the other sides.
- [ ] **Pixel-overlap experiment (low priority):** neither Isopolis nor the isometric.nyc pages
      read so far mention a few-px overlap; both butt-join final quadrants with no blending.
      Keep `overlap_px` = 0 unless the 3×3 test shows edge artefacts; if needed, crop, never blend.
      → renders are pixel-exact at `overlap_px` 0 (Phase 2 test). The ~3 px overlap question now
        only concerns *generated* tiles; test it in Phase 5 with `stitch_block.py`.
- [ ] Batch runner that can be stopped/resumed and runs overnight.
- [ ] **Review app** (small local web page): shows generated quadrants on top of a real map,
      click to reject/regenerate, see render vs result side by side. Expect to spend real
      time here — this is where quality comes from.

Deliverable: every quadrant in the pilot area approved.

## Phase 6 — Assemble and cut the tile pyramid (1 day)

- [x] Stitch approved quadrants into one huge image (`pyvips`, handles images bigger than RAM).
      Crop each generated window to its exact quadrant rects (drop the `overlap_px` margin).
      → `pipeline/build_pyramid.py`: `arrayjoin` over the plan's tile grid (missing tiles
        transparent), crops `overlap_px` via `screen_rect_px`. Uses `pyvips[binary]` (bundled
        libvips 8.18, no Homebrew). Done on render tiles for the prototype; for generated art the
        input will be quadrants, so this needs a quadrant mode later.
- [x] Cut a pyramid: `vips dzsave` (Deep Zoom) or `z/x/y` tiles, WebP or PNG, 256/512 px.
      → Deep Zoom, 512 px, no overlap. `--style photo` = WebP Q85 + box shrink; `--style pixel` =
        lossless WebP + nearest (placeholder until the palette-aware downscale below). Writes
        `manifest.json` (origin in plan screen px, north dir, screen→lon/lat affine, attributions).
        Pilot: 10240×6144, 15 levels, 333 tiles, 12 MB, ~4 s.
      Isopolis: level 0 = the quadrants themselves, each level up box-downsamples 2×2 children.
- [ ] Lower zoom levels: downscale carefully (box filter, then optional palette snap) so
      the art doesn't turn to mud. Compare a few methods side by side.
- [ ] Optional: pack into a single **PMTiles** file for easy hosting.

Deliverable: `dist/tiles/` (or `dist/map.pmtiles`).

## Phase 7 — Web viewer (2–3 days)

- [x] OpenSeadragon (good for one giant image) or Leaflet with `CRS.Simple`.
      → `viewer/` (Vite + OpenSeadragon 6). `npm run viewer -- dev --map ../dist/<map>` or `build`,
        which writes a self-contained static site into the map folder. Mini-map, compass from
        `north_screen_dir`, lat/lon under the cursor (ground level), attribution from manifest.
        Tested headless: deep links, coords, no console errors, also as a plain static site.
- [ ] `image-rendering: pixelated` at high zoom, smooth at low zoom.
      → `style: pixel` switches smoothing off and allows 8× zoom; per-zoom switching not done yet.
- [x] Camera position in the URL hash (`#x,y,zoom`) so views can be shared, like tinyrj.
      → x,y in plan screen px (stable across rebuilds and between render/pixel versions), zoom =
        screen px per map px.
- [ ] Nice extras later: compass, place labels, click a neighbourhood for info, mini-map,
      day/night palette swap, small animated details (boats, cars) as sprite overlays.

## Rough budget (pilot area)

- Nano Banana Pro example generation: a few hundred images.
- Fine-tuning: a few GPU-hours.
- Generation: one model call per tile (pilot ≈ hundreds to low thousands of tiles).
- Hosting: tiles for a pilot area are typically well under a few GB → near-free on R2.
Check current prices with each provider before starting.

## Known risks

| Risk | Mitigation |
|---|---|
| Google 3D Tiles terms restrict use | **Confirmed** (Phase 0): no storing, derivatives, AI training or resale. Open-data source needed for anything public/paid (1b) |
| Seams between tiles | Half-tile sliding-window infill + seam planner + review app (Isopolis still had some seams where two windows collide) |
| Water, trees, glass look wrong | Over-represent them in training pairs |
| Style drifts across the map | Fine-tuned model + palette snapping |
| Muddy zoomed-out levels | Careful downscaling (Phase 6) |
