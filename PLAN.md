# Isometric pixel-art city map — project plan

Goal: a zoomable, pannable isometric pixel-art map of a real city, in the spirit of
isometric.nyc and tinyrj.com, that can become a **paid game**. Every tile is generated by an
image model from an isometric 3D render of the city, and the result is served as a static tile
pyramid. Because of the commercial goal, all source data must allow commercial derived works:
we use the **OSM+Lantmäteriet option** (decided 2026-11-04), not Google.

Pilot area: **Södermalm, Stockholm** (placeholder — change in `config/area.yaml`).
Start small (≈1–2 km²), prove the whole pipeline end to end, then scale.

## Status (2026-11-04)

- **Done:**
  - Planning, rendering and serving pipeline, independent of the data source: tile planner
    (`pipeline/plan_tiles.py`, 0.25 m/px, 1024 px tiles of 2×2 quadrants, north-up camera at

    check (`pipeline/stitch_block.py`), Deep Zoom pyramid (`pipeline/build_pyramid.py`) and

## Phase 2 — Isometric renderer

- [x] three.js scene with an **orthographic** camera at the fixed isometric angle.
      → camera basis, frustum and tile targets are read from the plan JSON, never recomputed.
- [x] `renderTile` → PNG, headless via Playwright, batch export.
      → `npm run render -- render --plan … --out data/renders/<area> --block=… | --tiles=… |
        --tiles-file … | --all`. Skips renders already made for the same tile geometry (resumable),
        transparent background = no data, JSON sidecar per tile. `--source test` = synthetic box city.
        Headless Chromium uses the real GPU (`--use-angle=metal`).
- [x] Grid planner (`pipeline/plan_tiles.py`) in isometric screen space.
      → quadrants are the canonical unit. Infill windows at any quadrant offset are cut from the base
        renders via `window_rect_px()`; no extra renders needed.
      → tile ids `x_y` = screen column/row. North-up: `x`+1 = 256 m east, `y`+1 = 512 m south
        (ground); north points straight up.
- [x] Verify seams on a 3×3 block (test scene and Google): neighbours' shared pixels identical
      (test scene) / mean ≤ 0.023 (Google, float rounding at triangle edges). `overlap_px` = 0 is
      enough for renders; changing it shifts edge pixels slightly, so re-render everything if it
      changes. The "step ratio" seam metric depends on content (water inflates it).
- [ ] Repeat the 3×3 seam check for `--source osm` and `--source lm`.
- [ ] Optional extra passes (masks, depth): see Phase 1a step 3.

Deliverable: `data/renders/<area>/{x}_{y}.png` for the whole pilot area, from open data.

## Phase 4 — Fine-tune our own model

Why: consistent style across thousands of tiles, cheaper/faster than a cloud model per tile,
and can run locally on the user's NVIDIA GPU.

- [ ] Choose a base image-editing model that supports LoRA fine-tuning **and allows commercial
      use** (Phase 0 licence check).
- [ ] **Two tasks in one model:**
  1. *Generate*: render → pixel art.
  2. *Infill*: render + already-finished neighbour quadrants (pasted in) → pixel art that
     continues them seamlessly. Build these inputs by masking parts of the Phase 3 pairs.
     Isopolis: 4-bit TL/TR/BL/BR masks (1 = keep as context, 0 = generate), all 15 patterns.
- [ ] Reference point: Isopolis used Qwen-Image-Edit-2511 + LoRA r=16, 2,000 steps, 1× H100;
      a 100-pair set beat a 60-pair set.
- [ ] Train, then evaluate on held-out tiles: style match, geometry faithfulness, seams.
- [ ] Iterate on data, not just hyperparameters (add more water/tree examples — known weak spots).

Deliverable: a model + `pipeline/generate.py` that calls it.

## Phase 5 — Generate the whole map

- [ ] SQLite database (`data/map.db`) with one row per **quadrant**: position, render path,
      generated PNG, status (`pending / generated / approved / rejected`), notes.
- [ ] Generation order: **sliding 1024² window, stepped by half a tile (1 quadrant)**, so
      every window after the seeds has ≥1 finished quadrant as context (Isopolis §2d: "slide
      by half image in any direction"; isometric.nyc does the same with quadrant infill).
      Seed a few windows, then a seam planner greedily grows outward in waves (Isopolis: 440
      renders → 1,519 generations in 67 waves, ~3.5× calls). Rules (isometric.nyc tasks/012,
      019): don't generate a window between finished quadrants on opposite sides; fill strips
      as 2×1 blocks with 1-quadrant gaps, then the gaps. Each window writes only its
      mask-0 quadrants.
- [ ] Rejection guard: compare each generation to a baseline (context-free) inference of the
      same window; regenerate if it drifts too far in style/palette.
- [ ] Water: skip windows above a water threshold and stamp a water texture instead.
- [ ] Regenerate a bad quadrant by placing a 2×2 window with verified context on the other sides.
- [ ] **Pixel-overlap experiment (low priority):** renders are pixel-exact at `overlap_px` 0; the
      ~3 px overlap question only concerns *generated* tiles. Test with `stitch_block.py`; if
      needed, crop, never blend.
- [ ] Batch runner that can be stopped/resumed and runs overnight.
- [ ] **Review app** (small local web page): shows generated quadrants on top of a real map,
      click to reject/regenerate, see render vs result side by side. Expect to spend real
      time here — this is where quality comes from.

Deliverable: every quadrant in the pilot area approved.

## Phase 6 — Assemble and cut the tile pyramid

- [x] Stitch tiles into one huge image (`pyvips`, handles images bigger than RAM).
      → `pipeline/build_pyramid.py`: `arrayjoin` over the plan's tile grid (missing tiles
        transparent), crops `overlap_px` via `screen_rect_px`. `pyvips[binary]` (bundled libvips

- [x] Cut a pyramid: Deep Zoom, 512 px, no overlap. `--style photo` = WebP Q85 + box shrink;
      `--style pixel` = lossless WebP + nearest (placeholder). Writes `manifest.json` (origin in
      plan screen px, north dir, screen→lon/lat affine, attributions).
- [ ] Lower zoom levels: downscale carefully (box filter, then optional palette snap) so
      the art doesn't turn to mud. Compare a few methods side by side.
- [ ] Optional: pack into a single **PMTiles** file for easy hosting.

Deliverable: `dist/<map>/` (or `dist/map.pmtiles`).

- [ ] Nice extras later: place labels, click a neighbourhood for info, day/night palette swap,
      animated details (boats, trains, buses on real timetables via Trafiklab, as tinysthlm does).

## Rough budget (pilot area)

- Extra work for the open-data scene vs Google: ~1–2 weeks (step 1 test: 2–3 days).
- Image-model example generation: a few hundred images.
- Fine-tuning: a few GPU-hours (or local GPU).
- Generation: one model call per quadrant window (pilot ≈ hundreds of calls).
- Hosting: tiles for a pilot area are typically well under a few GB → near-free on R2.
Check current prices with each provider before starting.

## Known risks

| Risk | Mitigation |
|---|---|
| Open-data renders lack facades and texture, so the art is less faithful / more generic | Step 1 test first; then add structure (masks, window grids, facade colours, roofs) only where needed; hand-care for landmarks |
| Image-model licence blocks commercial use (e.g. Qwen-Image 2.1: "Non-commercial use only") | Check each model's licence (outputs and weights) before Phase 3/4 |
| Existing Stockholm map: **tinysthlm.com** ("Tiny Stockholm", Audrius, launched 2026-10-27, WIP): Google 3D Tiles → Qwen-Image 2.1 + tiny.london LoRA, live SL transit. Free, non-commercial | Differentiate: paid game, own style, clean open-data licence |
| Outdated / changing city (Slussen: per OSM parts are still being built; Lantmäteriet photos 2025-05) | OSM is current; patch affected quadrants with the user's own reference photos; re-render when new data arrives |
| Lantmäteriet legal review / GDPR terms take time or restrict use | Order early; OSM covers step 1 meanwhile |
| Seams between tiles | Scene-fixed colours, half-tile sliding-window infill + seam planner + review app |
| Water, trees, glass look wrong | Over-represent them in training pairs; IR-band vegetation mask |
| Style drifts across the map | Fine-tuned model + palette snapping |
| Muddy zoomed-out levels | Careful downscaling (Phase 6) |
